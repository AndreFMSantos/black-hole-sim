# v2.2f-b — GRMHD snapshot reader (Illinois) and `--disk-model grmhd` mode

André's decision (2026-11-12): option 1 (reader), then option 3 (run the GRMHD ourselves); the neural network is set aside ([22f2-neural-compression](22f2-neural-compression.md)); the interactive mode is treated as a performance question (final section). Context: [22f-grmhd-snapshot](22f-grmhd-snapshot.md), [22b-radio-torus](22b-radio-torus.md), sources in [references](../REFERENCES.md).

## Pipeline
1. **`code/tools/convert_grmhd.py`** (HDF5 → `.bgm`, numpy float64, 2.4 s per snapshot): builds the native FMKS metric `g = Jᵀ g_KS J` (with analytic `dθ/dX1` and `dθ/dX2`), `u^μ` and `b^μ` with the pyharm conventions, and writes per cell `ρ, Θ_i = (Γ−1)UU/ρ, |b|, β = P_g/P_mag, u^μ_KS, b̂^μ_KS` (12 `float32`, 226.5 MB). Invariants over **all** 4.72 M cells, in float64: `|u·u + 1| ≤ 9e-14`, `|b̂·u| ≤ 1.7e-14`.
2. **`core/include/bhs/grmhd.hpp`**: `Fmks` (θ, derivatives and **inverse** by Newton with bisection), `ks_inverse`, `load_bgm`.
3. **GPU (`render.cu`)**: 3 `float4` 3D textures (`(ρ, Θ_i, |b|, β)`, `u^μ`, `b̂^μ`) with hardware trilinear filtering, periodic φ (`wrap`), r and θ with `clamp`. At each sample: `X1 = ln r`, `X2` by inverting `θ(X1,X2)`, `φ_KS = φ_BL + ∫a/Δ dr`; reprojects `u` (solves `u^t` from `u·u = −1`) and `b` (`b·u = 0`, `|b̂| = 1`).
4. **Photon in KS:** `p_t = −1`, `p_φ = L`, `p_r^BL = ±√R/Δ`, `p_θ = ±√(M/(1−μ²))` (with the ray's `L`, `Q`: null by construction in BL; signs from the integrator state), **`p_r^KS = p_r^BL + (2r − aL)/Δ`** (from `t_KS = t_BL + ∫2r/Δ dr`, `φ_KS = φ_BL + ∫a/Δ dr`).
5. **Emission:** `E = −p·u`, `g = E_obs/E`, `cos θ_B = (p·b̂)/E`, `n_e = ρ ρ_unit/(m_p + m_e)`, `B_G = |b| B_unit` (`ρ_unit = M_unit/L³`, `B_unit = c√(4π ρ_unit)`), `Θ_e` by `--electrons const` (`Θ (m_p/m_e)/(1 + Ti/Te)`, pyharm convention), `rhigh` (`Ti/Te = (R_high β² + 1)/(1 + β²)`) or `prop` (`Θ_e = c Θ`); synchrotron and transport as in the radio mode (v2.2b).

Flags: `--disk-model grmhd --grmhd dump.bgm [--munit 1e26 --mbh 6.5e9 --electrons const|rhigh|prop --ti-te 3 --rhigh 20 --th-e-ratio 1 --nu-ghz 230 --tb-range 8,11 --grmhd-step 0.05]`. The spin comes from the dump.

```bash
uv run --with h5py --with numpy python -I tools/convert_grmhd.py torus.out0.05500.h5 MAD_a0_5500.bgm
build/apps/v3_1-kerr-cuda-ui/v3_1-kerr-cuda-ui --shot g.png --grmhd MAD_a0_5500.bgm --disk-model grmhd --theta 17 --dist 150 --fov 14 --w 700 --h 700 \
  --prec float --samples 1 --munit 1e26 --mbh 6.5e9 --electrons rhigh --rhigh 20 --nu-ghz 230 --tb-range 8,11 --tonemap aces --grmhd-step 0.03
```

## Oracles
Core (`test_grmhd.cpp`, 5 new cases, **137 in total**): `θ(X1,X2)` and its two derivatives against the **numpy** of `convert_grmhd.py` (11 points, reference generated by script) to 1e-13; `θ(0)=0, θ(½)=π/2, θ(1)=π` and strictly increasing; inverse `θ → X2` to 1e-10 (including `X2 = 1e-4` and `0.9999`) and refusal of `θ` outside [0, π]; `ks_inverse` really is the inverse (independent 4×4 product); `.bgm` file round trip.

GPU (`--selftest`, section `v2.2f`):
| Test | Result |
|---|---|
| inverse FMKS map on the device (X1, X2 in cell fractions) | 2.3e-5 |
| at the cell centres the texture returns the stored values (2000 cells): ρ, Θ_i, \|b\|, β | **0 (exact)** |
| same for `u^μ` and `b̂^μ` (abs.) | 4.8e-7 |
| interpolated at 3000 points: `u·u = −1`, `b·u = 0`, `b·b = 1` with the KS metric | 4.4e-7 |
| **null condition** `g^{μν}p_μp_ν = 0` in KS along 256 rays | 7.9e-4 (limit 5e-3) |
| **torus oracle**: analytic torus in BL (v2.2b) against the *same* torus written by `tools/make_torus_dump.py` (numpy, independent of the C++) and read by the reader (FMKS/KS): ratio of totals | **0.99723** (641 rays) |
| same, per-ray error | median **2.2e-3**, p95 5.7e-3 |

The torus oracle tests the whole chain (Python generator → `.bgm` → textures → FMKS inverse → photon momentum in KS → `u^μ` and `b̂^μ` → field angle → emission) against an independent implementation in BL. Mean difference between the two images: **0.065/255** (ratio of means 0.9990).

## What went wrong (and what was refuted)
1. **`θ(X2)` inversion with 14 iterations:** 0.017 cells of error at `i = 18, j = 125` (near the pole `dθ/dX2 ≈ 15`, Newton falls back to bisection: 2⁻¹³ = the resolution of 14 steps). I detected it with a cell-by-cell test of the inverse map. With 40 iterations (exit on convergence) the centres became **exact**.
2. **Two hypotheses of mine refuted by measurement:** (a) "the 8-bit weights of the hardware filter": manual interpolation with float weights gave **more** error (8.7e-3 vs 7.8e-3) and, after the fix, the hardware gives 0 at the centres; I removed the manual path. (b) "`acosf` near the pole": the cell has `θ = 2.80` rad (FMKS compresses θ at small r), it was not even near the pole.
3. **Null condition at 2e-2** with `p_r`, `p_θ` from a Hermite of `dr/dτ'`, `dμ/dτ'`: near the horizon the Hermite fails. With `±√R/Δ` and `±√(M/(1−μ²))` it dropped to 1e-4 and the test came to validate only the transformation to KS.
4. **The torus oracle failed at first** (reader 19 % brighter, saturated grey disk in the shadow): my Python generator left `h > 1` next to the hole (`|u_t| → 0`, `h → ∞`; `ρ̃ = 7e3` at `r = 2.3`), an **unbound** region of the torus; the analytic renderer already excluded `r < 0.7 r_in`. A defect of the test, not of the reader; fixed in the generator.
5. **Fine ripples near the ring** with a fixed step: insufficient sampling, because the FMKS radial cell at r ≈ 6 is only `r dX1 = 0.13` M. The step became **proportional to r** (`--grmhd-step`, fraction of r, ≤ 2 M).

## And the interactive mode? Measured
**Cost per frame** (1 sample/pixel, static snapshot, RTX 5080):
| Resolution | step 0.15·r | step 0.05·r |
|---|---|---|
| 640×360 | 32.3 ms (31 fps) | 43.5 ms (23 fps) |
| 960×540 | 67.9 ms (15 fps) | 93.0 ms (11 fps) |
| 1280×720 | 117.3 ms (8.5 fps) | 160.6 ms (6.2 fps) |
| 1920×1080 | 256.2 ms (3.9 fps) | 348.8 ms (2.9 fps) |

**Loading a snapshot** (226 MB, with the file in the OS cache): **44–45 ms** until the 3D textures. The machine has 63 GB of RAM (34.6 GB available) and 16 GB of VRAM (1.4 GB already in use).

**Storage over time:** at 20 M/s of disk time and snapshots 5 t_g apart, that is **4 snapshots per second**: 226 MB × 4 ≈ 0.9 GB/s of reading. Loading costs ~25 % of the time budget (cached) and ~50 % cold (estimated ≈ 75 ms of reading alone at 3 GB/s NVMe): it fits in a background thread with 3–4 resident snapshots (0.9 GB of VRAM). Two minutes = 480 snapshots = 108 GB in this `float32` format, which does not fit in RAM (63 GB): disk *streaming* is needed.

**Conclusions (with what is not measured flagged):**
- **Static interactive at 360p–540p is viable** (11–31 fps measured); at native 1080p (3–4 fps) it is not.
- **With time evolution** one must interpolate between two snapshots (twice the texture reads): **not measured**, I estimate ~1.5–2× slower, so ~10–15 fps at 360p. It is an estimate, not a measurement.
- Levers not yet measured: empty-space skipping with a bounds map (the emission ends at r ≈ 30), `float16` textures, fewer sub-samples where the field is smooth, and low-resolution rendering with upscaling or temporal reprojection.
- Without optimisation, interactive at native 60 fps is out of reach; what you get today is an explorer at 10–30 fps at low resolution.

## v2.2f-c part 2: time interpolation between snapshots (v4_0, the v4 refactor branch, 2026-11-16)
`--grmhd-next F --grmhd-tau T [--grmhd-dt M] [--grmhd-pattern P]` (and the UI: play + "interpolate in time"). Two snapshots are resident as texture sets; the sampler reads snapshot A at `phi - P Omega_K T dt` and B at `phi + P Omega_K (1 - T) dt` and blends all fields linearly (u^mu and b^mu are re-normalised afterwards by the existing reprojection). Playing forward swaps the sets and loads ONE snapshot (28 ms, float).
- **Exactness:** T = 0 and T = 1 reproduce the static snapshots bit for bit; also after the swap (ctest `v4_0_grmhd_blend`, `--selftest-blend DIR`).
- **Pattern speed measured, not assumed.** Against the middle snapshot of triplets of our own MAD run (300/301/302, 350/351/352, 380/381/382, 420/421/422, 450/451/452; 480x270, image MAE in 8-bit units; dt = 4 M assumed from the 2 M spacing), mean over the 5 triplets: no shift 0.108, **P = 0.2: 0.072 (-33 %)**, P = 0.1: 0.082, P = 0.3: 0.079, P = 0.5: 0.132, **P = 1 (full Keplerian): worse than no shift (0.28 vs 0.10 on one triplet)**. A single snapshot is 0.17-0.32 off. The emitting pattern therefore turns at ~0.2 of the Keplerian rate; default `--grmhd-pattern 0.2`. Caveat: one run, one frequency (230 GHz), the 2 M spacing is the UI's statement, not re-measured.
- **Cost with 2 snapshots (I estimated 1.5-2x; measured +10 %):** 960x540 20.8 -> 22.9 ms, 1920x1080 77.4 -> 85.4 ms (with r_cap 30).
- **Streaming:** loading a snapshot is 28 ms (float), of which 13 ms is the file read and parse. v4_0 now parses the snapshot after the next on a worker thread (`grmhd_prefetch`), so the render thread only does the ~15 ms upload (in the selftest, right after the call, the wait is 7.8 ms; during playback it has a whole snapshot period to finish). Not measured under real playback. `float16` loads are slower (142 ms, CPU conversion), so the half-precision option does not help streaming.

## Limitations (to declare)
- **a ≠ 0 validated (2026-11-16; external benchmarks added 2026-11-19):** on our own MAD dump (`mad_00100.bgm`, a = 0.9375), ctest `v3_1_grmhd_spin` (`BHS_GRMHD_TEST` selects the dump): cell-centre values returned by the texture = stored values (relative 0, absolute 9.5e-6 for `u^μ`, `b̂^μ`), KS invariants `u·u = −1`, `b·u = 0`, `b·b = 1` at 3000 interpolated points to 1.4e-6, **photon null condition in KS along 256 rays 3.7e-4** (limit 5e-3, so `p_r^KS` is right), inverse FMKS map 7.6e-6 cells. **Update 2026-11-19:** (1) `tools/make_torus_dump.py` extended to arbitrary spin: analytic BL torus vs KS reader at `a = 0.9, i = 60°` agrees to **`0.99824` (`−0.18 %`)**, median per-pixel relative error `1.57e-3`; (2) direct comparison with `ipole` on Illinois `MAD_a+0.94` (frame 5500, `T_p/T_e = 3`) agrees to **`+0.47 %`** in flux (`0.10813` vs `0.10762 Jy`, L1 `5.45 %`, median pixel ratio `1.0012`).
- **Static snapshot** in v3_1 (no time); v4_0 interpolates between consecutive snapshots (above), without any dynamics between them.
- **Polar axis:** the FMKS grid converges there; you see a central bright point and a polygonal shadow at 17°. In `float`, `μ = cos θ` loses precision near the poles.
- **`M_unit` and the electron model are free**: calibrated to M87* / Sgr A* in v2.2b3 / note 41. The `R_high` formula is verified against Mościbrodzka et al. 2016 and `ipole` (note 41). The rule `Θ_e < 0.3 ⇒ no emission` and Dexter's fit (valid for `Θ_e > 3`) underestimate the cold emission (`--emission leung` is the calibrated default).
- **`U1..U3` convention verified (2026-11-19):** directly confirmed in `AFD-Illinois/iharm3d/core/phys.c:162-173` (`ucon_calc`: `u^i = P[U1+i-1] - gamma * alpha * g^{0i}`).
- Hardware trilinear filter also on `u^μ` and `b̂^μ` (renormalised afterwards); the interpolation does not preserve `∇·B = 0`.
